## 三、为什么否决 ES（BM25）这条路

这是本次最重要的一个「不做」。它对应 b.md 里的 `sparse_recall` 节点。

**BM25 的真实收益**：向量检索对**精确专有名词**（人名、功法名、型号、订单号）召回不稳 ——
「罗峰」和「雷神」在 1024 维空间里可能很近，BM25 靠词频能一刀切开。这是向量检索的真短板。

**但代价是**：

1. 新增 Elasticsearch 集群：内存开销大（默认堆 1G+）、要额外做备份、要做健康检查；
2. 中文分词要装 **IK 插件**：非官方插件，必须版本严格对齐、从源码编译，容器化还要自制镜像；
3. **数据双写一致性**：`ebook8` 里有多少条切片，ES 里就得有同样的多少条，重灌、增量、失败重试都要两套逻辑；
4. 与现有容器编排（docker-compose：mysql / app / nginx）叠加，运维对象从 3 个变 4 个。

**换句话说**：为了让「罗峰」这种人名召得更准，要引入一个比整个应用还重的组件。

**更划算的替代路径**（按性价比排序）：

| 路径 | 收益 | 成本 | 状态 |
|---|---|---|---|
| 重排（cross-encoder） | 直接解决「Top-5 里混入不相关片段」，把真正相关的顶上来 | 1 次 API 调用，零迁移 | ✅ 已做 |
| 查询改写 + 多路 RRF | 换措辞命中不同切片，覆盖更全，**不需要重建集合** | 1 次小模型 + N 次 embedding | ✅ 已做（默认关） |
| Milvus 内置 BM25（`FunctionType.BM25`） | 稀疏路召专有名词，**不引入新组件** | 需重建集合并重灌全量数据 | ⏸ 待定，见 03 文档 |
| ES + IK | 同上 | 新集群 + 插件 + 双写 | ❌ 否决 |

注意第三行：**Milvus 2.5 自己就带 BM25**（`SPARSE_FLOAT_VECTOR` 字段 + `FunctionType.BM25` Function），
SDK `@zilliz/milvus2-sdk-node@3.0.3` 也确实有 `hybridSearch()` / `RANKER_TYPE.RRF`。
所以「要 BM25」和「要 ES」是两件事 —— 参考实现选 ES 是因为它那套是教学 demo，
不是为了证明 ES 更适合本项目。**先确认 Zilliz Cloud Serverless 版本支持 BM25 Function，再谈要不要做。**

## 四、为什么用 RRF 而不是「分数加权求和」

| 维度 | 分数加权求和 | RRF |
|---|---|---|
| 跨通道可比性 | COSINE ∈ [0,1]，BM25 无上界 → **不可比** | 只用排名，天然可比 |
| 是否需要归一化 | 需要（min-max / z-score），而归一化依赖当次结果分布，**极不稳定** | 不需要 |
| 参数数量 | 至少 1 个权重，且要调 | 1 个 `k`，论文给了经验值 60 |
| 丢失的信息 | 保留分数绝对信息 | 丢掉「有多相关」，只留「相对更相关」 |
| 适合的位置 | 最终排序 | **初召回融合** |

结论：RRF 只用来融合初召回，**真正的相关性判断交给后面的 rerank（cross-encoder）**。
RRF 丢掉的「绝对相关度」正好由重排分补回来 —— 两个组件各司其职，不是重复劳动。

`k=60` 来自论文 *Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods*，
作用是压低头部名次差异，避免「第一名通吃」：

```js
score = Σ 1 / (60 + rank)     // rank 从 1 开始
// 名次 1 → 1/61 = 0.01639
// 名次 2 → 1/62 = 0.01613   （差 1.6%，而不是 2 倍）
```

## 五、预算拆分：先采纳，后被实测推翻

**这是本次唯一一个「先照抄、再改回去」的决策，也是最有价值的一条复盘。**

### 参考实现的做法

```js
const ES_K = 15, MILVUS_K = 15;
const n = Math.max(1, qs.length);              // 4 条问句
const kEach = Math.max(2, Math.ceil(ES_K / n)); // ceil(15/4) = 4 → 4×4 = 16 ≈ 15
```

理由听起来非常正确：**「扩大召回」不等于「成本翻倍」**，把同一份预算摊到多个角度上，
用更多角度换更高覆盖，总候选数还不变。

### 它在参考实现里为什么是对的

参考实现的两路是 **ES(BM25) 与 Milvus(向量)** —— **异构通道**。
同一批文本，一路按词频打分、一路按语义打分，召回的**本来就是不同的东西**。
两路各给一份预算互不浪费，合并才是「扩大覆盖」。

要提醒的是：**参考实现的收益主要来自通道异构，而不是来自「拆分」本身。**

### 照搬到本项目为什么是错的

本项目 Phase 3 的多路是 **4 条同义改写问句，全部走 Milvus 稠密检索** —— **同类、同通道**。

同义问句的检索结果**高度重叠**（本来就是同一个问题的不同说法），此时再按路数拆预算，
等于把每一路都砍到只剩头部几条，并集反而比单路**更小**。

**实测（同一问题、同一次运行条件）：**

| 方案 | 每路取几条 | 融合后候选数 |
|---|---:|---:|
| 单路宽召回（基线） | 15 | 12 |
| 4 路 × `ceil(15/4)` = 4（参考实现的拆分） | 4 | **6** ❌ |
| 4 路 × 15（本项目做法） | 15 | **15** ✅ |

拆分后候选从 12 掉到 6 —— **「用更多角度换更高覆盖」的前提根本不成立**，
因为角度并没有带来新的候选，只带来了预算的稀释。

### 更深一层的原因：RRF 的前提被破坏了

RRF 的公式 `Σ 1/(60 + rank)` 融合的是**排名列表**。
一条文档排在某一路第 1 名，代表「在这一路的检索意图下它最相关」——
这个「第 1 名」是**有信息量**的。

但如果每路只取 4 条，那么「第 1 名」是在一个被人为切碎的短列表里的第 1 名。
更糟的是：**一条原本在某路排第 12 的文档，拆分后直接不出现了**，
RRF 连给它算分的机会都没有。

> **一句话总结**：预算拆分适合「多个互不相同的检索通道」，
> 不适合「同一个通道的多种问法」。前者是分摊，后者是稀释。

### 本项目的做法

```js
// 每条问句都给足 wideK，让 RRF 在「多个各自完整的排名列表」上找共识
for (const q of queries) {
  lists.push(await retrieveRelevantContent(q, wideK))
}
const candidates = rrfFuse(lists, { topK: wideK })  // 仍截回 wideK，候选池大小恒定
```

代价是 embedding 调用数与 Milvus 检索次数变成 N 倍（这是**必须付的**，因为要拿到 N 个完整列表）；
但 `rrfFuse` 的 `topK: wideK` 把候选池截回 15 条，所以**重排的 token 成本不变**。
费用增长只发生在 embedding 这一侧，且被 `QUERY_AUGMENT_ENABLED=false` 默认关掉了。

### 这条复盘的通用价值

**同一个技术手段，放在不同的架构约束下，结论会反转。**
「参考项目这么做」不构成理由，必须回到「它当时面对的是什么通道、什么数据分布」。
本次是靠**实测数字（6 vs 12）**发现并修正的 —— 如果只看代码逻辑，
「总量不变、角度更多」这个说法毫无破绽，能骗过所有人（包括写代码的人自己）。
