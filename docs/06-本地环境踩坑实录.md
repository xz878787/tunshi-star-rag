# 06 · 本地环境踩坑实录：孤儿进程、容器冲突、证书缺失与数据卷救援（2026-09-29）

> 本文与检索架构无关，记录的是一次「`docker compose up` 起不来」引发的连环排查。
> 五个坑彼此独立、又环环相扣：从一句「服务怎么自己停了」开始，先后牵出了
> 进程链、容器标签、TLS 证书、数据卷、端口映射五层问题。
> 所有命令均为 Windows PowerShell 实测可用版本，可直接复制排障。

## 一、坑一 · Ctrl+C 之后服务还活着：pnpm 三层进程链与孤儿 node

### 现象

终端里 `pnpm start` 启动成功、横幅打完，**提示符却自己回来了**，像是进程退了；
可浏览器访问 `localhost:3000` 依然是 HTTP 200。更怪的是：在当前终端按 Ctrl+C
「杀不掉」任何东西，重新启动还会莫名报 `EADDRINUSE`。

### 排查：别信提示符，问操作系统

```powershell
netstat -ano | findstr :3000        # → LISTENING，PID 56776 还在监听！
Get-CimInstance Win32_Process -Filter "ProcessId=56776" |
  Select-Object ProcessId, ParentProcessId, CommandLine, CreationDate
```

还原出的进程链是完整的三层：

```
PowerShell（你现在看的这个终端，并不是启动服务的那个）
└─ pnpm start                          (PID 50848)
   └─ cmd.exe /c node src/server.js    (PID 2380)
      └─ node src/server.js            (PID 56776，孤儿，仍在监听 3000)
```

### 根因

Windows 上 `pnpm start` 是 **pnpm → cmd → node 三层嵌套**。Ctrl+C 的信号
（或 Trae 预览终端回收任务时）只杀到顶层包装壳，node 子进程漏网成为孤儿。
而孤儿归属的那个 shell（PID 64048 的 pwsh）**并不是你眼前这个终端**——于是：

- 提示符回来 ≠ 进程死了，只是 shell 拿回了控制权；
- 孤儿不是当前终端的前台进程，**在当前终端按 Ctrl+C 永远够不着它**——这就是「无法杀进程」；
- 孤儿还占着 3000 端口，下次启动自然冲突。

### 处置

```powershell
taskkill /PID 50848 /T /F     # /T 连根拔起整棵树，三层一次杀干净
netstat -ano | findstr :3000  # 复查：无输出 = 端口已释放
```

### 教训

1. **判断服务死活看端口，不看提示符**：`netstat -ano | findstr :3000` 有输出 = 还在跑；
2. 本地启动改用 **`node src/server.js` 直启**：只有一层进程，Ctrl+C 一按就真死、端口立刻释放；
3. 万一再遇到杀不掉的孤儿，按端口一条命令清场：

```powershell
Get-NetTCPConnection -LocalPort 3000 -State Listen |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

## 二、坑二 · compose 不认「手工容器」：--force-recreate 也绕不过的名字冲突

### 现象

`docker compose up -d --force-recreate app` 报错：

```
Conflict. The container name "/rag-mysql8" is already in use by container "4b079cc1...".
You have to remove (or rename) that container to be able to reuse that name.
```

疑惑点：都 `--force-recreate` 了，为什么 compose 不直接重建？

### 排查：看容器的 compose 标签

```powershell
docker inspect rag-mysql8 --format '{{json .Config.Labels}}'
# → {}                                              ← 标签全空，黑户！
docker inspect tsxkrag-app --format '{{json .Config.Labels}}'
# → {"com.docker.compose.project":"tsxkrag", ...}    ← 正规军
```

### 根因

compose 只通过 **labels（`com.docker.compose.project` 等）** 认领自己创建的容器。
旧的 `rag-mysql8` 是两天前手工 `docker run` 起来的「无标签黑户」：compose 既不能复用它，
也不会替你删它——`--force-recreate` 只对「自己人」生效。名字撞车，直接罢工。

### 处置

```powershell
docker inspect rag-mysql8 --format '{{json .Mounts}}'   # ① 先看数据挂哪（见坑四，这步救了数据）
docker rm -f rag-mysql8                                  # ② 删容器（不带 -v，卷保留）
docker compose up -d --force-recreate app                # ③ compose 建自己的
```

### 教训

**删容器前先看 Mounts**；手工起过的容器，要么尽早交给 compose 管，要么在命名上避让。

## 三、坑三 · nginx 崩溃循环五周：一行 [emerg] 日志破案

### 现象

`tsxkrag-nginx` 状态永远是 `Restarting (1)`，`RestartCount` 累计 **4020** 次——
它已经安静地崩溃循环了五周，期间无人察觉（应用流量根本没走它）。

### 排查

```powershell
docker logs --tail 15 tsxkrag-nginx
# → [emerg] cannot load certificate "/etc/nginx/certs/fullchain.pem":
#          BIO_new_file() failed ... No such file or directory
```

compose 把 `./deploy/certs` 挂载进容器的 `/etc/nginx/certs`，而本地这个目录是**空的**——
真证书是服务器专属文件，按安全规矩从不进 git。于是本地 nginx 每次启动都死在加载证书这一行。

### 处置：本地自签证书（只求把服务跑起来，不追求信任链）

```powershell
openssl req -x509 -nodes -newkey rsa:2048 -days 3650 `
  -keyout deploy\certs\private.key -out deploy\certs\fullchain.pem `
  -subj "//CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

docker compose up -d --force-recreate nginx
```

两个细节值得记住：

- `-subj` 里的 `//CN=localhost` 双斜杠是 Git-Bash/MSYS 的路径转义风格，会有一条
  `Skipping unknown subject name attribute "/CN"` 警告——**无害**，证书照常生成；
- `.gitignore` 必须确保 `deploy/certs/` 被忽略（本项目已有该规则，`git check-ignore -v` 验证），
  防止自签私钥乃至未来真证书被误提交。

结果：`https://localhost → 200`，`http://localhost → 301`（自动跳 HTTPS，符合 nginx.conf 预期）。
浏览器提示「证书不安全」属自签正常现象，点继续即可；服务器上是真证书，不受影响。

**教训：崩溃循环先看 `docker logs` 再猜配置**——RestartCount 只告诉你它病了多久，
日志里那行 `[emerg]` 才是病历。

## 四、坑四 · 「数据没了」：匿名卷与命名卷的错位，以及一次完整的数据救援

### 现象

容器重建后打开应用，用户数据全部消失。

### 根因：新旧容器挂的根本不是同一个卷

| 容器 | 数据卷 | 卷类型 | 内容 |
|---|---|---|---|
| 旧（手工 docker run） | `058e98ff…` | **匿名卷** | 11 用户 / 33 会话 / 305 消息 ✅ |
| 新（compose） | `tsxkrag_mysql-data` | **命名卷** | 更早的旧数据（几乎为空） |

compose 的 `volumes:` 声明只认**命名卷**；旧容器匿名挂载的数据，新容器天然看不见。
「数据没了」不是丢了，是**换了卷**。

### 救援全流程（全程容器内 UTF-8，不经宿主机转码）

```powershell
# ① 把匿名卷挂到一个临时 mysql 容器上（数据卷仍在磁盘，随时可挂回）
docker run -d --name rag-mysql8-recover `
  -v 058e98ff…:/var/lib/mysql mysql:8.0

# ② 导出：--result-file 写在容器内，绕开 shell 重定向与 PowerShell 编码问题
docker exec -e "MYSQL_PWD=$pw" rag-mysql8-recover `
  mysqldump -uroot --single-transaction --databases rag_system --result-file=/tmp/dump.sql

# ③ 搬运：容器对容器拷贝
docker cp rag-mysql8-recover:/tmp/dump.sql $env:TEMP\rag-dump.sql
docker cp $env:TEMP\rag-dump.sql rag-mysql8:/tmp/dump.sql

# ④ 导入：source 命令让 mysql 自己读文件，避免管道转码
'source /tmp/dump.sql' | docker exec -i -e "MYSQL_PWD=$pw" rag-mysql8 mysql -uroot

# ⑤ 验证：11 / 33 / 305 —— 与旧卷完全一致 ✅
```

### 教训

1. **命名卷 + compose 是唯一正道**，手工 `docker run -v 匿名卷` 迟早付出代价；
2. `docker rm -f` 不带 `-v` 时卷永远还在——先别慌，`docker volume ls` 找回来；
3. dump/导入全链路让数据**只在容器之间流动**（mysqldump → docker cp → source），
   绝不经过 PowerShell 管道（PS 5.1 会按系统编码重排字节，中文必乱码）。

## 五、坑五 · 数据库 GUI 连不上了：3307 端口的失而复得

### 现象

DataGrip 连接 `localhost:3307` 报 `Connection refused: getsockopt`。

### 根因

`3307` 是旧容器当年手工 `-p 3307:3306` 映射出来的；compose 文件里的 mysql 服务
**刻意不发布任何宿主机端口**（只允许 app 走内网访问）。旧容器一删，GUI 的门自然就没了。

### 处置：本地覆盖文件，而非修改主 compose

直接改 `docker-compose.yml` 加 `ports:`，会把 3307 一并带到服务器——服务器 MySQL 不应对外暴露。
正确姿势是利用 compose 的**自动覆盖机制**，新建 `docker-compose.override.yml`：

```yaml
# 本地开发专用：MySQL 暴露到宿主机回环地址，供本机 GUI 直连；已 gitignore，勿提交
services:
  mysql:
    ports:
      - "127.0.0.1:3307:3306"
```

`docker compose up -d mysql` 重建后，`Test-NetConnection localhost -Port 3307` 由 False 变 True，
GUI 原有连接配置**一个字都不用改**，重连即恢复。同时把该文件加入 `.gitignore`
（`git check-ignore` 验证生效），服务器环境完全不受影响。

**教训：本机与服务器配置有分歧时，用 override 文件承载差异**，主 compose 永远保持「服务器安全态」。

## 六、附录 · PowerShell 调 docker 的两个引号陷阱（本次反复踩到）

**陷阱一：`--format` 模板里带点的 map 键。** Go template 的
`{{index .Config.Labels "com.docker.compose.project"}}` 在 PowerShell 下引号被剥，
报 `function "com" not defined`；就算写成 `{{json .Config.Labels.com.docker.compose.project}}`
也会因点号被当嵌套字段而返回 `null`，让人误判「容器没有 compose 标签」。
正解：整包导出 `{{json .Config.Labels}}`，一次看全、零歧义。

**陷阱二：Windows PowerShell 5.1 向原生命令传参会剥掉内层双引号。** 类似
`docker exec c sh -c 'mysql -uroot -p"$PW" -e "select 1"'` 的嵌套引号，到容器里已经面目全非。
实测可靠的替代模式——密码走环境变量、SQL 走 stdin 管道，全程零内层引号：

```powershell
'show databases;' | docker exec -i -e "MYSQL_PWD=$pw" rag-mysql8 mysql -uroot
```
