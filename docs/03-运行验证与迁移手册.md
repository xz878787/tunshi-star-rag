## 二、冒烟验证（3 步）

### 第 1 步：只看重排自身（不依赖 Milvus / MySQL）

```js
import { DashscopeRerank } from './src/rerank/dashscopeRerank.mjs'

const reranker = new DashscopeRerank({
  apiKey: process.env.OPENAI_API_KEY,
  model: 'qwen3-rerank',
  topN: 2,
  baseUrl: process.env.RERANK_URL,
})
const ranked = await reranker.compressDocuments(
  [
    { id: 'd1', score: 0.61, chapter_num: 3,  content: '量子计算是计算科学的前沿领域，与本题无关。' },
    { id: 'd2', score: 0.58, chapter_num: 45, content: '罗峰高考成绩不足以进入顶尖学府，于是选择加入极限武馆获取修炼资源。' },
    { id: 'd3', score: 0.72, chapter_num: 46, content: '极限武馆会为学员提供功法与修炼资源，罗峰希望借此快速提升实力。' },
  ],
  '罗峰为什么选择加入极限武馆'
)
console.log(ranked)
```

**期望**：返回 2 条；无关的 `d1` 被排到最后未进入 top2；每条都有 `rerankScore`；
**`score` 仍是原来的 0.58 / 0.72（不是 0~1 的重排分）**。

实测输出：

```
d2 rerank=0.9518 score=0.58
d3 rerank=0.8405 score=0.72
```

注意 `d2` 的向量分（0.58）比 `d3`（0.72）**更低**，但重排后 `d2` 排到了第一 ——
重排在纠正向量检索的顺序，这正是它存在的意义。

### 第 2 步：验纯函数（不花钱）

```js
import { rrfFuse } from './src/rag/hybridRetrieval.mjs'

rrfFuse([[{ id: 'a' }, { id: 'b' }], [{ id: 'b' }, { id: 'c' }]])
// → b > a > c    （b 两路都命中，RRF 分 1/62+1/61 = 0.0325）

rrfFuse([[{ id: 'x' }, { id: 'y' }, { id: 'z' }]])
// → x, y, z      （单路退化为恒等变换）
```

**期望日志**：

**期望断言**：

| 断言 | 含义 |
|---|---|
| `state.documents.length > 0` | 检索有结果 |

| `state.documents.every(d => d.rerankScore !== undefined)` | 重排确实生效 |

## 三、实测数据（2026-09-25，本地）

问题 `罗峰为什么选择加入极限武馆？`，`k=5`，`maxRetrievalCount=2`，`RERANK_CANDIDATE_K=15`

| 轮次 | 宽召回候选 | 重排保留 | 最高重排分 | 本轮最高 COSINE |
|---|---:|---:|---:|---:|
| 1 | 12 | 5 | 0.9772 | 0.7321 |
| 2 | 11 | 5 | 0.9538 | 0.7484 |

**结论 1：重排确实在改变顺序。** 第 1 轮第 10 章的片段 COSINE 只有 0.7040（5 条里排第 4），
重排分 0.9772 排第 1 —— 这就是「按向量分选出的 Top-5 ≠ 最相关的 5 条」的实证。

**结论 2：宽召回未足额。** 请求 15 条只返回 11~12 条，怀疑与 `IVF_FLAT` 默认 `nprobe`
只探测部分簇有关，未深挖。因为最终只保留 5 条，不影响效果。

**结论 3：`lastTopScore` 反而变高了**（0.7484）。这是宽召回的**必然副作用** ——
候选变多，最大值单调不减。它导致 0.55 阈值判断**略微宽松**，详见下方「已知副作用」。

**补充：打开查询改写（`QUERY_AUGMENT_ENABLED=true`，改写 3 条）后的同一问题**

```
查询改写：新增 3 条问句，走多路召回
重排完成：候选15条 → 保留5条，最高重排分0.9078
最终   lastTopScore=0.7577
```

多路召回下 `rrfFuse(lists, { topK: wideK })` 把候选池截回 15 条，
所以**候选池大小与重排成本不随路数增长** —— 增长的只有 embedding 调用次数。
去掉预算拆分前后的对比（6 → 15）见 `docs/README.md` 实测数据 §B。

## 四、已知副作用与处置

**现象**：库外主题（本该触发联网兜底）在宽召回后可能不再跌破 `0.55`。

**原因**：`LOW_SCORE_THRESHOLD = 0.55` 是在「5 条候选」上标定的（库内 0.63~0.77 / 库外 0.4~0.55）。
换成 15 条候选后，max 天然抬高，两个区间都往上移。

**处置（三选一）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| ① 不动 | 先观察 | 库外问题可能少触发联网，靠路由的 `web` 分支兜底 |
| ② 关宽召回 | `RERANK_CANDIDATE_K=5` | 完全回到改造前行为，同时放弃重排的收益 |
| ③ 重新标定（推荐） | 用评测集跑出正负样本的分数分布，把阈值抬到新区间的分界点 | 需要真实标注数据 |

本次**没有**擅自改阈值 —— 改一个没重新标定过的阈值，比不改更危险。

### 为什么现有集合不能直接用

`src/main.mjs` 建的 `ebook8`：

```js
{ name: 'content', data_type: DataType.VarChar, max_length: 10000 }   // ← 没有 enable_analyzer
{ name: 'vector',  data_type: DataType.FloatVector, dim: 1024 }
```

BM25 需要三个东西，一个都没有：

1. 一个 `enable_analyzer = true` 的 VARCHAR 文本字段（要配中文 analyzer）；
2. 一个 `SPARSE_FLOAT_VECTOR` 字段存稀疏向量；
3. 一个 `FunctionType.BM25` 的 Function，把文本字段自动映射成稀疏向量。

**这三样都不能加到已有集合上并自动回填历史数据**，所以必须新建集合 + 重灌。

### 迁移步骤（**关键省钱点：不需要重新 embedding**）

现有集合里 1024 维向量都是现成的，直接读出来写进新集合即可，
**不用再调一次 `text-embedding-v3`**（否则几千次串行 embedding 在免费档 QPS 下要跑很久）。

```js
// 步骤 1：新建集合（结构示意，需按实际 SDK 版本核对字段名与 Function 写法）
const NEW = 'ebook8_v2'
await client.createCollection({
  collection_name: NEW,
  fields: [
    { name: 'id',          data_type: DataType.VarChar, max_length: 100, is_primary_key: true },
    { name: 'book_id',     data_type: DataType.VarChar, max_length: 100 },
    { name: 'book_name',   data_type: DataType.VarChar, max_length: 200 },
    { name: 'chapter_num', data_type: DataType.Int32 },
    { name: 'index',       data_type: DataType.Int32 },
    // ① 开 analyzer 的文本字段（BM25 从这里生成稀疏向量）
    { name: 'content', data_type: DataType.VarChar, max_length: 10000,
      enable_analyzer: true, enable_match: true, analyzer_params: { type: 'chinese' } },
    // ② 稠密向量：与现有集合完全一致
    { name: 'vector', data_type: DataType.FloatVector, dim: 1024 },
    // ③ 稀疏向量：由 Function 自动写入，insert 时不需要传
    { name: 'content_sparse', data_type: DataType.SparseFloatVector },
  ],
  // ④ BM25 Function：content → content_sparse
  functions: [{
    name: 'bm25_fn',
    type: FunctionType.BM25,
    input_field_names: ['content'],
    output_field_names: ['content_sparse'],
  }],
})

// 步骤 2：建索引（稠密沿用 COSINE；稀疏用 SPARSE_INVERTED_INDEX + BM25）
await client.createIndex({ collection_name: NEW, field_name: 'vector',
  index_type: IndexType.IVF_FLAT, metric_type: MetricType.COSINE, params: { nlist: 1024 } })
await client.createIndex({ collection_name: NEW, field_name: 'content_sparse',
  index_type: IndexType.SPARSE_INVERTED_INDEX, metric_type: MetricType.BM25 })

// 步骤 3：搬数据（不重新 embedding！）
//          注意 output_fields 必须显式带上 'vector'，否则读不到向量
let offset = 0
while (true) {
  const rows = await client.query({
    collection_name: 'ebook8',
    filter: `id != ""`,                 // Milvus query 必须带 filter
    output_fields: ['id', 'book_id', 'book_name', 'chapter_num', 'index', 'content', 'vector'],
    limit: 1000, offset,
  })
  if (!rows.data?.length) break
  await client.insert({ collection_name: NEW, data: rows.data })  // 不带 content_sparse，由 Function 生成
  offset += rows.data.length
}

// 步骤 4：切换（改 ragGraph.mjs 顶部的 COLLECTION_NAME，或改成读 env）
// await client.loadCollection({ collection_name: NEW })
```

> ⚠️ 上面的 `functions` / `analyzer_params` 字段名必须对照**你实测的 SDK 版本**（当前 3.0.3）
> 和 Zilliz Cloud 文档核对 —— 不同版本字段名有差异。**先在测试集合上跑通，别直接对线上动手**。

### 代码侧要改的一处

`retrieveWithRerank` 的 ③ 之后再 push 一路稀疏召回，然后 RRF 一起融合：

```js
// 现有
for (const q of queries) lists.push(await retrieveRelevantContent(q, wideK))
// 新增（示意）
lists.push(await sparseRecall(question, wideK))   // BM25 路，返回同构对象（score 用 BM25 分）
// 后面的 rrfFuse / 重排 / 阈值逻辑一行都不用改
```

`rrfFuse` 本来就是「任意 N 路」，融合层不需要改动 —— 这就是本次把融合写成通用形态的收益。

**但注意 §三 的边界 1**：稀疏路的 BM25 分**不能**进 `topScore`。
`topScore` 必须只取稠密路的 COSINE 分，否则 0.55 阈值再次失效。
