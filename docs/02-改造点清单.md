# 改造点清单（文件级 / 函数级）

> 全部改动共 **3 个新增文件 + 3 个修改文件**，`ragGraph.mjs` 主图结构**一个节点、一条边都没动**。
> 唯一被替换的是检索这一层：`retrieveNode` 内部改调 `retrieveWithRerank()`。

## 一、新增文件

### 1. `src/rerank/dashscopeRerank.mjs` — 重排器（Phase 1）

```js
new DashscopeRerank({ apiKey, model, topN, baseUrl })
  .compressDocuments(documents, query) → Promise<Array>
```

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 文档格式 | 取正文时兼容 `.content` 与 `.pageContent` | 本项目是普通对象，参考实现取 `.pageContent` 会拿到 `undefined` |
| 分数保真 | 返回 `{...原对象, rerankScore}`，**不动 `score`** | `score` 是 COSINE，被 0~1 重排分覆盖会毁掉 `afterRetrieve` 的 0.55 阈值 |
| 配置来源 | 构造参数显式传入，**类内不读 env** | 避免「哪个模块先加载 .env」这种隐式依赖（参考实现用 `import "dotenv/config"`，本项目按模块位置解析 .env，两套混用会踩坑） |
| 错误处理 | 非 2xx 用 `text()` 取原始错误体再抛；返回结构异常也抛 | 与项目里 `bochaWebSearch` 的错误处理风格一致 |
| 调用方兜底 | 由 `retrieveWithRerank` 统一 try/catch | 重排是增强不是必需，失败要降级不能中断 |

继承 `BaseDocumentCompressor` 只是为了对齐 LangChain 生态的接口名（将来可直接塞进
`ContextualCompressionRetriever`），它是个**没有任何构造逻辑的抽象类**，对普通对象零副作用。

### 2. `src/rag/queryAugment.mjs` — 查询改写（Phase 3）

```js
augmentQuery(chatModel, query, count) → Promise<{ queries: string[] }>
buildRetrievalQueries(original, augmentation) → string[]
```

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 结构化输出 | `chatModel.withStructuredOutput(QueryAugmentSchema)` | 项目里路由/拆解/规划都是这套写法，不用手写 `JSON.parse` + 剥 ```json |
| 数量 | `min(1).max(5)`，可配，**不补齐** | 参考实现 `length(3)` 不足时用原问题补齐 → 白白多一次重复召回 |
| 失败降级 | catch 后返回 `{ queries: [] }` | 上层 `buildRetrievalQueries` 会退化成只检索原问题，链路不受影响 |
| 去重 | 与原问题、与彼此都去重 | 改写模型经常把原问题原样吐回来 |
| 顺序 | `buildRetrievalQueries` 把**原问题固定放第 0 位** | 保证「只取第一条」时行为与改造前一致，也保证 RRF 单路退化时排序不变 |

Prompt 里明确要求「**专有名词必须原样保留**」——这是查询改写最容易出事的地方：模型手一滑把
「罗峰」改成「主角」，检索直接偏航。

### 3. `src/rag/hybridRetrieval.mjs` — 融合层

```js
rrfFuse(rankedLists, { k = 60, topK }) → Array   // 纯函数，无 IO
```

整个文件只有一个纯函数，**没有任何 IO 和依赖注入**，所以可以直接单测（本次已验证 5 个断言）。

> 参考实现的 `kEach = ceil(total/n)` 预算拆分**没有**搬过来 —— 实测它在本项目的
> 「同类同通道多问句」场景下会把候选数从 12 拉到 6。完整推演见
> [01-参考实现拆解与选型决策.md](./01-参考实现拆解与选型决策.md) §五。

`rrfFuse` 写成「任意 N 路」的通用形态，不是「两路」：

```js
for (const list of rankedLists ?? []) { ... }   // 1 路=恒等，2 路=稠密+稀疏，N 路=N 条改写问句
```

这一点是为 Phase 2 留的：落地 BM25 时只需要**再 push 一路**，融合逻辑一行都不用改。
`rrfFuse([[...]])` 单路时退化为恒等变换，所以「开关查询改写」不需要在调用处写 if/else 分支。

> **Phase 2 已落地，验证了这个判断**：混合检索接入时 `rrfFuse` 确实**一行没改**，
> 只是调用处从 `rrfFuse(lists, ...)` 变成 `rrfFuse([...denseLists, ...sparseLists], ...)`。
> Phase 2 的完整改造点见 [04-混合检索.md](./04-混合检索.md) §十。
> 同时补了一条 Phase 1/3 没料到的约束：**跨通道分数不可比**（COSINE ≤1 vs BM25 无上界），
> 所以融合列表的**顺序**变成语义的一部分（稠密路在前 → 同 id 保留 COSINE），
> 且 `mergeUnique` / `formatSources` 需要按 `channel` 字段做守卫。

**改动 3：新增 `retrieveWithRerank()`（约 L116-171）**

`retrieveRelevantContent` **保持原样未动** —— 它的签名被 `eval/run-project-eval.mjs` 依赖，
改签名会连带改评测脚本，不符合「改动最小」。

新增的 `retrieveWithRerank(question, k)` 返回 `{ docs, topScore, reranked }`：

| 步骤 | 代码 | 说明 |
|---|---|---|
| ① 宽召回量 | `wideK = reranker ? max(k, RERANK_CANDIDATE_K) : k` | 不重排就不宽召，避免白拿用不上的片段 |
| ② 改写（可选） | `augmentQuery` → `buildRetrievalQueries` | 关闭时 `queries = [question]` |
| ③ 逐路召回 | `for (const q of queries) await retrieveRelevantContent(q, wideK)` | 每条问句**各取满 wideK**；**串行**执行（DashScope QPS），且不做预算拆分（见 01 文档 §五） |
| ④ RRF 融合 | `rrfFuse(lists, { topK: wideK })` | 单路=恒等；`topK` 截回 wideK，保证候选池大小恒定 → 重排 token 成本不随路数涨 |
| ⑤ 阈值依据 | `topScore = max(COSINE)` | 只认 COSINE |
| ⑥ 重排 | `reranker.compressDocuments(candidates, question)` | 失败降级为 COSINE 顺序前 k 条 |

### `.env` / `.env.example`

`RERANK_URL` 是**必填项**，且地址必须是 **DashScope 原生协议**：

```
✅ https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank   （实测 200）
❌ https://dashscope.aliyuncs.com/compatible-mode/v1/reranks                        （实测 404）

```

这套 **input/parameters 包壳**，就是原生协议的形状 —— 所以它配的一定是原生地址。
`compatible-mode` 是 OpenAI 兼容层，只代理了 chat/embeddings，**没有代理 rerank**。

## 三、四条语义边界（改这一层之前必须确认）

| # | 边界 | 违反的后果 |
|---|---|---|
| 1 | `topScore` / `lastTopScore` 恒为 **COSINE** 分，不能掺重排分 | 阈值判断静默失效，低分联网兜底再也不触发 |
| 2 | 重排**不改每条文档的 `score` 字段**，只改顺序和条数 | `mergeUnique` 拿重排分和 COSINE 分比较，多轮去重的「保留更高分」变成随机行为 |
| 3 | 多路召回必须**串行** | DashScope 免费档 QPS 限流，并发会批量 429 |
| 4 | 增强全关时，行为必须与改造前**逐字等价** | 无法安全回退；线上出问题只能改代码而不是改变量 |

第 4 条是本次能做到「改动最小」的核心：`RERANK_CANDIDATE_K=5` + `RERANK_ENABLED=false` +
`QUERY_AUGMENT_ENABLED=false` 三个值一设，检索层的行为和改造前**完全一致**（同一次 `search`、
同样的 k、同样的分数、同样的顺序、同样的 `topScore`）。

## 四、回退矩阵

| 现象 | 操作 | 效果 |
|---|---|---|
| 重排接口挂了/超时 | `RERANK_ENABLED=false` | 回到纯向量 Top-K（代码里也有 try/catch 自动降级） |
| 检索变慢但想保留重排 | `RERANK_CANDIDATE_K=8` | 候选减半，重排 token 减半 |
| 想完全回到改造前 | `RERANK_CANDIDATE_K=5` | 宽召回关闭，行为逐字等价 |
| 多路召回太慢 | `QUERY_AUGMENT_ENABLED=false` | 回到单路 |
| 重排把好片段排丢了 | `RERANK_TOP_N=8` | 让 LLM 看到更多依据，代价是 prompt 变长 |
| 库外问题不再触发联网 | 调高 `LOW_SCORE_THRESHOLD`，或 `RERANK_CANDIDATE_K=5` | 见 `docs/README.md` 的「已知副作用」 |

## 五、预留但**未实现**的扩展点

1. **BM25 稀疏路**：`rrfFuse` 已支持 N 路，落地时在 `retrieveWithRerank` 的 ③ 之后再 push 一路
   `sparseRecall()` 并 push 进 `lists` 即可，融合与重排逻辑不用动。前提是集合先迁移（见 03 文档）。
2. **重排分参与阈值**：目前 `rerankScore` 只用于观测。若将来想用「重排分低」判断库内没料，
   需要**重新标定**一个新阈值（不能复用 0.55，量纲不同）。
3. **多轮结果统一重排**：现在每轮各自重排保留 5 条，3 轮后累计约 15 条给 LLM。
   另一种做法是「只在本轮宽召回、最后一轮对累计池统一重排」。本方案没选它，因为
   **用原始整句去重排一个跨子问题的异构池，会把某个子问题专属的证据挤掉** ——
   每轮用自己的子问题做排序依据，语义更聚焦。
