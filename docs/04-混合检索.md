# 04 · 混合检索（ES BM25 稀疏路 + Milvus 稠密路）

> 目标：把检索从「只有一条向量通道」升级为**真异构双通道** —— ES 的 BM25 词面召回 +
> Milvus 的向量语义召回，用已有的 RRF 融合，再交给已有的重排器精排。
> 全文所有数字都来自本机实测，不是估算。

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 混合检索是不是必须上 ES？ | **本机演示/开发是**（ES 8.17 + analysis-ik，真倒排 + 真词法打分）；线上 ECS 上不了 ES，用**进程内 BM25** 兜住 |
| 要不要重建 Milvus 集合？ | **不要**。稀疏路只用 `id + 正文 + 章号`，向量继续留在 Milvus 里由稠密路查，**零 embedding 调用、零数据迁移** |
| 语料从哪来？ | 从 EPUB 按 `main.mjs` 同一套切片规则**重算**（11977 条），**不要**从 Milvus 全量拉 |
| 新增 npm 依赖 | 只有 `@elastic/elasticsearch@8.19.2`（对齐 ES 8.x 主版本）。进程内 BM25 是纯 JS，零依赖 |
| 默认开关 | `SPARSE_BACKEND=auto` —— 配了 `ES_NODE` 走 ES，没配走内存 BM25；置 `none` 一键回到改造前的纯向量 |
| 会不会污染 0.55 联网兜底？ | 不会。`topScore` 只取稠密路 COSINE，BM25 分**只参与排名**（见 §六.2） |

## 二、为什么要 ES：它和「查询改写多路召回」不是同一件事

之前的 Phase 3 已经能「多路召回」了，但那是**同一通道的多条问句** —— 4 条同义改写问句全部走
Milvus 稠密检索，Top-N 高度重叠（实测 4 路各取 15 条，并集只比单路多一点点）。

ES 这条路解决的是**完全不同的短板**：

| 通道 | 强项 | 弱项 | 实测同问句 Top10 重叠 |
|---|---|---|---|
| Milvus 向量 | 换种说法也能召回（语义近似） | 专有名词、精确术语容易漏 | — |
| ES BM25 | 人名/招式名/专有名词**字面命中**即高分 | 换个说法就召回不到 | **0~5 / 10** |

重叠只有 0~5 条，说明两路召回的东西**本来是互补的** —— 这正是 RRF（Reciprocal Rank Fusion）
被设计出来要解决的情景，也是 Phase 3 的「同类同通道多问句」做不到的。

**实测（同一问句，ES vs 进程内 BM25，各取 Top10 的 id 重叠数）**：

```
罗峰为什么选择加入极限武馆   → 重叠 5/10
混沌城主是谁                → 重叠 2/10
罗峰最后成为什么境界         → 重叠 0/10
```

## 三、线上为什么不能跑 ES（实测证据，别再试）

线上 `root@121.40.36.70` 实测：

| 指标 | 实测值 | ES 8 要求 | 结论 |
|---|---|---|---|
| 总内存 | **1.6 GiB** | 单节点至少给 1~2 GiB 堆+文件缓存 | ✗ |
| 可用内存 | **479 Mi** | — | ✗ |
| swap | **无** | — | ✗ 一旦超内存直接 OOM 杀进程 |
| CPU | 2 核 | — | 勉强 |
| `vm.max_map_count` | **65530** | **≥ 262144** | ✗ ES 启动即失败 |

而且这台机器上跑着 `tsxkrag-app` / `rag-mysql8` / `tsxkrag-nginx`，ES 一旦起来会把它们一起挤死。
所以线上方案是：**不部署 ES，用进程内 BM25**（`SPARSE_BACKEND=auto` 且不配 `ES_NODE` 时自动生效）。

> 进程内 BM25 的代价：常驻约 **177 MB heap / 438 MB RSS**、构建约 **2.4 s**（一次性，启动时预热）。
> 若线上内存吃紧，把 `SPARSE_BACKEND=none` 设上即可完全关闭稀疏路，回到纯向量检索。

## 四、语料为什么从 EPUB 重算，而不是从 Milvus 拉

三个数字必须记住：

| 数字 | 含义 | 来源 |
|---:|---|---|
| **12062** | Milvus 集合 `ebook8` 的 `count(*)` | Zilliz Cloud 实测 |
| **11977** | 从 EPUB 按 `main.mjs` 规则重算的切片数（**1523 章，跳过 34 个插图页**） | `npm run sync:es` 实测 |
| **10970** | 用 offset 分页从 Milvus 全量拉取能捞到的**唯一 id** 数 | 实测，见下 |

**Milvus 全量拉取被两条路证伪：**

1. `limit=16384` 单次拉取 → 响应体 **15.2 MB**，超过 gRPC 默认 **4 MB** 上限直接报错；
   显式传 `channelOptions` 把上限放宽到 100 MB **无效**（SDK 内部没透传）。
2. `offset` 步进分页能翻完不报错，但**有损**：页与页零重叠（说明不是分页错位），
   可每页比请求的条数少返 8~78 条 —— 最终只拿到 **10970 条唯一 id**，丢了约 1007 条。

**为什么必须 11000+ 条齐**：稀疏语料少 1000 条，就意味着这 1000 条切片**永远不会被 BM25 召回**，
而这恰恰是 ES 通道存在的意义（字面命中）。所以语料只能从 EPUB 重算。

**为什么重算能对齐 id**：`id = ${bookId}_${chapterNum}_${chunkIndex}`，`bookId` 恒为 `1`，
`chapterNum = 章节 0 基下标 + 1`，切片器 `RecursiveCharacterTextSplitter({chunkSize:500, chunkOverlap:50})`，
跳过 `chapterContent.length < 100` 的插图页 —— 这几条在 [sparseCorpus.mjs](file:///d:/test/demo-%E5%90%9E%E5%99%AC%E6%98%9F%E7%A9%BA1.0/tsxkRAG/src/rag/sparseCorpus.mjs)
里逐字复刻。只有 id 完全一致，RRF 才能把两路命中的**同一条切片**当成一条去重，而不是两条。

**id 对齐已实测验证**：取 ES Top5 的 id 去 Milvus 做 `id in [...]` 精确查询，**5/5 命中且章号一致**。

## 五、改造后的检索链路

```mermaid
flowchart LR
    Q["检索问句 q"] --> AW{"QUERY_AUGMENT_ENABLED"}
    AW -->|关| ONE["queries = [q]"]
    AW -->|开| MANY["queries = 改写N条 + q"]
    ONE --> D["稠密路 × N<br/>Milvus COSINE<br/>channel=dense"]
    MANY --> D
    D --> TS["topScore = max(COSINE)<br/>★ 只取稠密路"]
    ONE --> S
    MANY --> S
    S["稀疏路 × N<br/>ES BM25 / 进程内 BM25<br/>channel=sparse"] --> RRF
    D --> RRF["RRF 融合 score = Σ 1/(60+rank)<br/>稠密路在前 → 同 id 保留 COSINE"]
    RRF --> RR{"RERANK_ENABLED"}
    RR -->|开| CE["DashScope qwen3-rerank<br/>精排 → Top-K"]
    RR -->|关| SL["按 RRF 顺序取前 K"]
    CE --> OUT["documents<br/>score 仍是 COSINE（稀疏独有显示 '-'）"]
    SL --> OUT
    OUT --> MRG["mergeUnique<br/>跨轮去重：同 id 优先稠密路"]
```

## 六、关键设计（每条都是踩过或差点踩到的坑）

### 1. 中文分词：不用 jieba，用**二元 bigram**

- 不用 jieba 的理由：主流实现都是原生模块（node-gyp），在本机 Windows 编译、在服务器来回折腾，
  收益远小于风险。
- 实测 IK 的行为：`ik_smart` 把「罗峰」切成 `罗|峰`，`ik_max_word` 切成 `罗|峰`。**IK 会把人名拆成单字**，
  而 bigram 保留「罗峰」这个整体，人名命中率反而更高。
- 所以进程内 BM25 的分词规则是：连续 CJK 字符切**滑动二元组**（长度 1 的串保留单字），
  连续 ASCII 切整词并转小写，标点作分隔符。不做 CJK 单字索引 —— 倒排规模翻倍，收益靠 IDF 硬压，不值。

### 2. `topScore` 只能取稠密路 —— 最容易踩的坑

`afterRetrieve` 的 0.55 联网兜底阈值是**按 COSINE 标定**的（库内正常命中 0.63~0.77，库外 0.4~0.55）。
BM25 分**无上界**（实测同一条切片能到 **33.24**），一旦从融合后的候选集里取 max，阈值就永久失效。

```js
// ❌ 改造前（合并前只有一路，没问题；混入 BM25 后就是 bug）
const topScore = Math.max(...candidates.map((d) => Number(d.score) || 0))
// ✅ 现在：只从稠密路取，与 BM25 分彻底隔离
const topScore = Math.max(0, ...denseLists.flat().map((d) => Number(d.score) || 0))
```

### 3. 用 `channel` 标记守住「同一把尺子」

同一 id 可能被两路分别召回，而 COSINE（≤1）与 BM25（无上界）**不可比**：

- `rrfFuse` 里**稠密路放在前面** → 两路都命中的切片保留 COSINE 分（RRF 只保留首次出现的那个对象）；
- `mergeUnique` 跨轮去重时，**跨通道一律保留稠密路那条**，避免「只在稀疏路命中的 33 分」靠数值假象顶掉稠密路那条；
- 前端 sources 里，稀疏路独有的片段相似度显示为 `-`（与联网来源的 `-` 一致），
  不把 BM25 分冒充相似度。

### 4. 不做预算拆分（与参考实现的一处**刻意分歧**）

参考实现把总预算按路数均分（`kEach = ceil(K/n)`）。这在**异构通道**下是合理的，
但照搬到「同类同通道多问句」会降低覆盖（实测候选 12 → 6）。
本项目**每条问句、每条通道都给足 wideK**，让 RRF 在「多个各自完整的排名列表」上找共识。

融合后的保留条数仍是 `wideK`（= `RERANK_CANDIDATE_K`），也就是说：
**原始召回变宽了（两路 15+15≈30 条去重），但送进重排器的仍是 15 条** —— 重排成本不变。
想让重排看到更多候选，直接调大 `RERANK_CANDIDATE_K` 即可，无需改代码。

## 七、实测数据（本地，2026-09-25）

问题 `罗峰为什么选择加入极限武馆？`，`k=5`，`maxRetrievalCount=2`，`RERANK_CANDIDATE_K=15`。

| 配置 | 第1轮候选 | 第2轮候选 | 最终库内片段 | 其中稀疏路独有 | `lastTopScore` | 耗时 |
|---|---:|---:|---:|---:|---:|---:|
| `SPARSE_BACKEND=auto`（**ES**） | 15 | 15 | **8** | **3** | 0.7484 | 19.1 s |
| `SPARSE_BACKEND=none`（纯向量基线） | 12 | 11 | 10 | 0 | 0.7484 | 18.2 s |

**ES 路独有的 3 条切片**（纯向量完全没召回）：

```
1_30_3  第30章  很快考核成绩出来——  拳力——3109kg！  速度——58m/s
1_10_4  第10章  “自由武者是不错。”罗峰摇头道，“不过，我不想让我爸妈担心。进入军校…
1_18_2  第18章  不过到底哪里可怕，网络上没详细说明。  “等你以后，成为武者之后。很…
```

**要诚实说明的一点**：这次单题实测里，混合检索的**最终片段数反而少了 2 条**（8 vs 10）。
原因不是「丢了召回」，而是：

1. RRF 把「两路共识」的切片排在前面，融合后仍截断到 15 条 → 池子里的**稠密路名额被挤掉一部分**，
   但换来的是跨通道共识排序；
2. 单题、多跳、每轮独立重排的场景下，命中重复（第 2 轮 5 条里有 2 条与第 1 轮重叠）会被 `mergeUnique` 去重。

**谁更好不能靠单题判断**，要看评测集上的召回率/答案准确率 —— 这属于下一步（见 §九）。
本阶段的确定收益是：**召回来源多了一路互补通道，且完全可开关、可回退**。

**三条读数（都由上表实测数字推导，非估算）**

1. **重排提升的是首位精度，不是覆盖率**：B 组首条命中 5→6，但 gold 章节条目从 16 **掉到 14** ——
   宽召回+重排会把一部分正确章节挤出 Top-5（Q2 / Q12 / Q14 就是这种）。
2. **稀疏路补回覆盖面**：C 组 gold 章节条目 19（反超基线 3 条），其中 **23 条片段是纯向量召不回、
   靠 BM25 字面命中救回来的**，且有 2 道题的首条直接由稀疏路摘得。
   → 结论是**两条增强互补，不是叠加冗余**（只加 B 反而比基线差）。
3. **`topScore` 逐位不变（0.7352）正是「分数尺子守卫」生效的证据**：若把 BM25 分混进 `max`，
   这个数会飙到 30+，0.55 的联网兜底阈值就静默失效了。

**必须主动划的边界**：有 **6 道题**（Q4 / Q5 / Q7 / Q9 / Q17 / Q20）三种配置都召回不到金标章节 ——
瓶颈在向量模型的语义匹配能力与标注/切分方式，**不是检索增强能解决的**。

## 八、配置与回退

| 变量 | 默认 | 作用 |
|---|---|---|
| `SPARSE_BACKEND` | `auto` | `auto`：配了 `ES_NODE` 走 ES，否则走进程内 BM25；`es`：强制 ES（没配地址=关闭）；`memory`：强制进程内；`none`：**完全关闭稀疏路** |
| `ES_NODE` | 无 | ES 地址（如 `http://localhost:9200`）。**线上不要配这一行** |
| `ES_INDEX` | `tsxk_starry_sky` | 索引名，`npm run sync:es` 按此名建索引 |
| `ES_ANALYZER` / `ES_SEARCH_ANALYZER` | `ik_max_word` / `ik_smart` | 写入/查询分词器；没装 IK 时 `syncEsIndex` 自动回落内置 `cjk` |
| `ES_RECREATE` | `true` | `sync:es` 是否先删索引重建（保证与语料全量对齐） |
| `ES_BULK_BATCH` | `500` | bulk 每批条数 |
| `ES_REQUEST_TIMEOUT` | `3000` | ES 单次查询超时；超时即降级返回空，不阻断问答 |

**回退路径（任选其一，都是改 env、不改代码）**

```
SPARSE_BACKEND=none          # 关掉稀疏路 → 纯向量（等价改造前）
RERANK_CANDIDATE_K=5         # 关掉宽召回
QUERY_AUGMENT_ENABLED=false  # 关掉查询改写
```
三者同时设置 = **行为与改造前逐字等价**。

   归因到稀疏路救回关键章节）。剩余可做的是**换更难的题集**（长尾专有名词、跨章节推理）拉开差距，
   以及把答案层评测接入 CI 固化。
2. **ES 与进程内 BM25 的排序不同**（实测 Top10 重叠 0~5 条），因为分词器与打分实现不同。
   这意味着「本机演示效果」和「线上效果」不会完全一致，线上验证要单独做一次。
3. **进程内 BM25 的常驻内存约 177 MB heap**，在 479 Mi 可用的 ECS 上是笔要盯着的开销。
   若要省内存，可以考虑把倒排表换成 `Int32Array`/`Uint16Array`（现在用的是扁平 JS 数组）。
4. **融合后的截断**（§六.4）会让稠密路在重排池里的名额被稀疏路挤占。
   如果评测显示纯向量命中的好片段被挤掉，可以把融合保留条数放宽到 `wideK × 通道数`，
   代价是重排的输入变多、延迟上升。
